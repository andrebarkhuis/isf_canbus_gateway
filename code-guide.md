# Code Style Guide

This guide defines coding conventions, file-organization rules and clean-code practices for the project
(C++17 on ESP-IDF). It is intended to be equally easy for people to read and for automated agents or linters
to parse.

> **One-pager promise:** Everything you need is on this page. No hidden rules elsewhere.

## 1 Folder & File Organization

| Area | Rule |
|---|---|
| **Source folders** | `src/can/` (IS F bus), `src/isotp/` (ISO 15765-2), `src/uds/` (Mode 21 protocol and definitions), `src/services/` (the two bus tasks' services), `src/mcp_can/` (MCP2515 driver), `src/logger/`. The translator sits at `src/` root because both services use it. |
| **Headers vs. sources** | Each `.cpp` has a matching `.h` with the same base name. Generated `.cpp` files (`uds_definitions.cpp`, `translator_table.cpp`) are declared in `uds/uds_mapper.h` and `message_translator.h`. |
| **Ported files** | A file ported from ToyotaLens names its source in its header comment and keeps ToyotaLens's names for constants, timers and methods, so the two can be compared side by side. |
| **Generated files** | Carry `// GENERATED by tools/generate.py` on line 1 and are never edited by hand. |
| **Platform headers** | Headers under `src/` include no ESP-IDF header unless the unit exists only on the device (`mcp_can`, `gt86_service`, `main`). Everything the host self-test compiles stays portable. |

## 2 Including Header Files

1. **Path from `src/`** — always the same path, never relative `../`:

   ```cpp
   #include "logger/logger.h"        // ✅
   #include "../logger/logger.h"     // ❌
   #include "logger.h"               // ❌ missing context
   ```

2. **Never include a `.cpp`.**
3. **Quote vs. angle-bracket syntax**

   | Use | Syntax | Example |
   |---|---|---|
   | Project headers | `"..."` | `#include "uds/uds_mapper.h"` |
   | C / C++ standard library | `<...>` | `#include <cstdint>` |
   | ESP-IDF, FreeRTOS | `"..."` | `#include "driver/twai.h"`, `#include "freertos/FreeRTOS.h"` |

4. Order: the unit's own header, a blank line, standard headers, a blank line, ESP-IDF headers, a blank line,
   project headers. Every `#include` starts at column 0.

## 3 Commenting

- Explain **why**, not **what**. Cite the ToyotaLens specification section (`§8.3`) or requirement (`R4.4`) a rule
  comes from.
- Use full sentences if the meaning is subtle; fragments are fine for obvious context.
- Prefer `// NOTE:` / `// TODO:` / `// FIXME:` prefixes for tools that harvest tasks.

## 4 Naming & Variables

| Guideline | Example |
|---|---|
| Descriptive, no abbreviations unless common | `errorCount`, not `errCnt` |
| No magic numbers | `constexpr uint32_t N_Cr_Ms = 1000;` |
| Members end in `_` | `rxId_`, `frameCount_` |
| Constants from the protocol keep ToyotaLens's names | `Services::ReadDataByLocalId`, `IsoTpTimers::P2StarMs` |

Before adding a new symbol, **search** the codebase (and ToyotaLens) to reuse existing ones.

## 5 Function & Class Design

- One purpose per function or class.
- Short functions; refactor beyond 40 lines unless the function is a straight port whose shape should stay
  recognisable.
- No dynamic allocation in the polling path; fixed-size buffers sized by the protocol (`MAX_UDS_PAYLOAD_LEN`,
  `ResponseDataMap::MaxLayoutLength`).
- No exceptions, no RTTI (disabled in `sdkconfig.defaults`).

## 6 Formatting

| Setting | Value |
|---|---|
| Indent | 4 spaces, no tabs |
| Max line length | 120 chars |
| Braces | **Allman** style: opening brace on its own line |
| File encoding | UTF-8 without BOM, LF line endings |

## 7 Verification

After any change:

```bash
python tools/generate.py        # if the frame spec changed; git status must stay clean otherwise
bash test/host/run.sh           # RESULT: PASS
.venv\Scripts\pio run           # the firmware compiles
```

## 8 Clean-Code Checklist

- [ ] Does each file include only what it needs?
- [ ] Any duplicated code that can be unified?
- [ ] Are all names self-explanatory?
- [ ] Are complex sections commented with **intent** and a specification reference?
- [ ] Are there unresolved `TODO`/`FIXME` tags?
